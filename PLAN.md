## Context

GoKid is an AI-powered flashcard and quiz app for UK primary school children (Reception–Year 6). A parent signs in, creates a profile for each child with their year group, and the app serves study sets generated by AI against the actual UK National Curriculum — not generic "age-appropriate" content. Cards are illustrated, quizzes are scored, and per-card mastery drives spaced repetition so the app gets smarter about what each child is weak on.

The repository is currently a bare Expo SDK 57 starter (React Native 0.86, React 19.2.3, expo-router ~57.0.4). Styling was stripped; there is no backend, no auth, no database. Everything below is greenfield.

The original brief asked for a UI prototype with three hardcoded dummy sets. That was rejected in favour of building backend-first: Basic Math, World Capitals, and Human Biology become **seeded, curriculum-linked rows in Neon**, so the API is testable immediately and nothing gets thrown away when the UI lands.

## Product spec

**Users.** The parent is the account holder and the paying customer. Children never authenticate — they are profiles under a parent, selected on a "who's studying?" screen. This is deliberate: children signing in with Google/Apple triggers COPPA verifiable-parental-consent obligations and most under-13s have no such account.

**Core loop.** Parent onboards → creates child profile (first name, year group) → child picks a set → flips illustrated cards → takes a quiz → gets a score → the app records every answer and schedules weak cards to resurface sooner.

**The "aha" moment.** The child's set is visibly *their* Year 3 maths, not generic maths — and it is already there, with pictures, instantly, with no loading spinner.

**In scope for v1**
- Clerk auth, Google + Apple only (no email/password)
- Parent account with N child profiles, each with a year group
- AI-generated study sets pinned to UK National Curriculum learning objectives
- Curated illustration library (batch-generated, human-reviewed, ImageKit-served)
- Flashcard view with flip, quiz mode with scored results
- Per-card mastery + spaced repetition (SM-2)
- Offline study with sync on reconnect
- Free tier with a hard server-side generation quota; paid subscription via RevenueCat

**Out of scope for v1**
- Manual set creation (the create screen from the original brief)
- Parent-uploaded homework photos / OCR
- Secondary school (Year 7+), exam boards
- Teacher/school accounts
- Web as a shipping target (it is a build artifact of the API host, not a product surface)

## Architecture

One Expo repo. The app and its backend ship from the same codebase.

```
Expo app (iOS + Android)  ──HTTPS + Clerk JWT──▶  Expo Router API routes
                                                   (EAS Hosting)
                                                        │
                          ┌─────────────────────────────┼──────────────────────┐
                          ▼                             ▼                      ▼
                    Neon Postgres                    Inngest              OpenRouter
                    (HTTP driver)              (generate-ahead jobs)   (per-job model)
                                                        │
                                                        ▼
                                                    ImageKit
                                             (illustration delivery)
```

### The constraint that shapes everything

**EAS Hosting runs on Cloudflare Workers (workerd) with `nodejs_compat` — not Node.** Two hard consequences:

1. **No raw TCP.** Neon must use `@neondatabase/serverless` (HTTP driver). `pg`/node-postgres cannot work, ever.
2. **Metro bundles all API routes and their dependencies into a single file, transpiled to CommonJS, with no dynamic-import support.** Any Node-first SDK will fail to bundle.

**Standing rule for server code: call REST over `fetch`; do not reach for vendor SDKs unless they earn their bundle weight.** Clerk, Neon, and Inngest earn it. ImageKit and Sentry-for-Node do not.

Anything that genuinely needs full Node (curriculum seeding, batch image generation, migrations, admin tooling) lives in `scripts/` and runs on the dev machine under `tsx`. That is the escape hatch, and it is a comfortable one.

### Verified package choices

| Concern | Package | Note |
|---|---|---|
| Auth (server) | `@clerk/backend` | `verifyToken` with `jwtKey` PEM → networkless, no JWKS round-trip |
| Auth (native) | `@clerk/expo` | successor to `@clerk/clerk-expo` |
| DB | `@neondatabase/serverless` + `drizzle-orm/neon-http` | HTTP driver |
| Jobs | `inngest` → `serve` from **`inngest/edge`** | `inngest/edge` returns `(Request) => Response`, matching Expo's route signature exactly. `inngest/cloudflare` does **not** — it wants the raw `(request, env, ctx)` Workers signature Expo never hands you. |
| Billing | `react-native-purchases` (client); webhooks verified with WebCrypto HMAC (server, no SDK) | |
| Images | URL building + WebCrypto signing by hand; `imagekit` SDK only in `scripts/` | the SDK pulls axios/form-data/lodash — unbundleable |
| Errors | `@sentry/react-native` (client); hand-rolled envelope client (server) | see below |
| UI | `@expo/ui` (46 SwiftUI / 57 Compose components, incl. layout primitives) + Reanimated 4 for the card flip | |

### Sentry, honestly

There is **no supported server-side path**. `@sentry/cloudflare` requires wrapping the worker's exported `fetch` handler, which Expo generates and owns. We write a ~60-line envelope client (`POST` to the Sentry envelope endpoint) called from a `withErrorReporting()` wrapper on every route, fired through `deferTask()` from `expo-server` so it never blocks a response. EAS Hosting's own dashboard captures uncaught route errors as a backstop. The client SDK works normally, and that is where the great majority of crashes will be.

## Data model

Governing principle:

> **Content is global and server-owned. Progress is child-owned and event-sourced. Mastery is derived, never synced as mutable state.**

**Content** (shared across every user — this is what makes generate-ahead affordable): `subjects` → `topics` → `learning_objectives` (keyed to UK NC statement codes, e.g. `Y3-MA-NPV-01`) → `study_sets` → `cards` → `card_images`. A study set is generated *against a specific learning objective*, which is what makes "tailored to their school plan" literally true rather than marketing copy.

**Identity**: `parents` (keyed by `clerk_user_id`), `child_profiles` (first name + year group + `birth_month`/`birth_year` — deliberately **not** full DOB, for UK AADC data minimisation), `subscriptions`, `usage_quota`.

**Progress** — the part that must be right on day one:

- **`card_reviews` is append-only and immutable**, keyed by a client-generated UUIDv7. Two devices studying offline produce two disjoint sets of rows. Sync is a **union** (`INSERT ... ON CONFLICT (id) DO NOTHING`). There is no conflict, by construction. Retries and duplicate pushes are free.
- **`card_mastery` is a deterministic fold over that log.** The server replays all reviews for an affected `(child, card)` pair in a total order — `(reviewed_at, device_seq, device_id, id)` — and recomputes SM-2 from scratch. Both devices converge on identical state regardless of sync order. The client's local copy is a disposable optimistic cache, always overwritten from the server.
- **Clock skew defence.** Kids change device clocks. On ingest, clamp `reviewed_at` into `[received_at - 30 days, received_at]`. Because `device_seq` is a monotonic per-device counter, within-device ordering survives a nonsense wall clock; worst case a card is mis-scheduled slightly. Work is never lost.

**Why this matters:** the naive design — sync `card_mastery` as a mutable row, last-write-wins — is broken. If a child studies 20 cards on the iPad offline and 15 on the phone offline, LWW silently discards one entire session and the parent watches progress vanish. It is invisible in testing (one device, always online) and catastrophic in production. **This is the single decision most likely to force a rewrite, so it lands in migration #1.**

**Sync cursor:** a single global sequence (`server_seq`) bumped by trigger on every insert *and* update. Not `updated_at` — Postgres stamps `now()` at statement time but rows become visible at commit time, so under concurrency a client can read past a row that later appears with an earlier timestamp and miss it permanently.

**Algorithm:** SM-2 for scheduling (ease 1.3–2.5, quality 0–5 derived from correctness + response-time buckets), with a Leitner box 1–5 as the kid-facing projection ("Learning → Getting it → Mastered"). The fold is a **pure function in `src/shared/srs.ts`, imported by both the worker and the app**, so on-device optimistic scheduling and server truth cannot drift.

## Offline sync

`expo-sqlite` + `drizzle-orm/expo-sqlite`. One Drizzle schema language for both Postgres and the on-device cache.

| Data | Direction | Authority |
|---|---|---|
| curriculum, published sets, cards, images | pull | **Server always wins.** Local copy is a pure cache — safe to nuke and refetch. |
| `card_reviews`, `quiz_attempts` | push | **Client. Append-only. Union.** Nothing ever wins or loses. |
| `card_mastery` | pull | **Server-computed.** Client holds an optimistic copy for instant UI. |
| `child_profiles` | push + pull | LWW on `updated_at`, server tiebreak. Low-stakes. |
| `subscriptions`, `usage_quota` | pull | Server. Never trust the client on entitlement. |

`POST /api/sync/push` is idempotent by construction — a flush that times out after the server committed is harmless. `GET /api/sync/pull?since=<server_seq>` paginates with a cursor.

**Generate-ahead:** keep ≥3 published, image-prefetched sets on device per child at all times. On foreground, check queue depth; if short, pull more, and if the server itself is short for that objective, emit an Inngest event to generate more. **The child is never blocked on an LLM call.** That is the entire purpose of the Inngest layer.

## Security rules (non-negotiable)

- **Every request is parent-authenticated and child-scoped.** The client sends a child id; the server *always* resolves it as `WHERE id = $child AND parent_id = $parent AND deleted_at IS NULL`. Never trust a child id alone. One forgotten `parent_id` predicate is a cross-family leak of children's data. This lives in a single `requireChild()` helper used by every route.
- **Auth checks go inside route handlers, not `+middleware.ts`** — middleware can short-circuit but has no clean way to hand a typed session down to the route.
- **Sign in with Apple is mandatory**, natively (App Store Guideline 4.8: offering Google without native Apple sign-in is an automatic rejection). A web-based Apple flow is a common rejection cause.
- **Parental gate** in front of the RevenueCat paywall and any external link.
- **Data minimisation:** first name + year group + birth month/year. No full DOB, no surname.

## Assumptions

1. **UK National Curriculum 2014**, Reception–Year 6, English/Maths/Science to start. Other subjects deferred.
2. **The three brief sets map to curriculum objectives**: Basic Math → Maths (number/place value), World Capitals → Geography, Human Biology → Science (animals incl. humans). They are seeded published sets, not hardcoded UI fixtures.
3. **Education category, 4+ rating — not the Kids Category.** Keeps Sentry and analytics permissible. A parental gate still ships.
4. **Free tier:** 1 child, ~20 AI generations/month, quota enforced server-side. Exact numbers to be tuned once real OpenRouter cost per set is known.
5. **Solo developer, no fixed deadline.** Phases are sequenced for correctness, not for a demo date.
6. **English (en-GB) only.** No i18n in v1.
7. **Illustration style** is a single consistent art direction, decided at Phase 5.

## Open risks

1. **Inngest may not bundle under Metro.** The mitigation (resolver stubs) is written, but unproven in this repo. *Escape hatch:* deploy `/api/inngest` as a standalone ~40-line Cloudflare Worker in the same repo, importing shared logic from `src/server/**`. It's a Worker, not a second framework — it doesn't violate the one-repo constraint, and it costs one `wrangler deploy` in CI. **This is why Phase 0 exists.**

   **⚠️ Deferring the EAS deploy defers the discovery of this risk, unless we guard against it.** Local development uses the Inngest Dev Server against Expo's local API routes, which run in **Node — not workerd**. Every Cloudflare-specific failure mode is therefore invisible locally. The guard is `npx expo export -p web` in CI from day one (Phase 0, Gate B): it needs no EAS account and no deploy, but it builds the real worker bundle. **Without that gate, this risk stays hidden until the first deploy, which is the worst possible moment to find it.**

2. **Sentry server-side is hand-rolled.** Accepted. Client SDK is unaffected.

3. **Neon's HTTP driver has no interactive transactions** — no `BEGIN; read; decide; write; COMMIT`. The append-only sync design sidesteps this entirely; `db.batch()` covers the rest. Escape hatch: `drizzle-orm/neon-serverless` WebSocket pool for a specific route.

4. **EAS env vars with `secret` visibility are NOT available to API routes.** `DATABASE_URL`, `CLERK_SECRET_KEY`, `INNGEST_SIGNING_KEY`, `OPENROUTER_API_KEY`, `IMAGEKIT_PRIVATE_KEY` must be created with **`--visibility sensitive`**. This will otherwise cost an afternoon of confused debugging. (Relevant from Phase 8.)

5. **The illustration review queue is human work that scales with curriculum coverage.** Someone must approve images. Currently unowned, and it will become a bottleneck before it becomes a crisis.

6. **AI question quality against the real curriculum is unvalidated.** A wrong Year 2 maths answer is worse than no app. Needs a human spot-check gate before any set is published, and ideally a teacher's eyes early.

7. **`@expo/ui` is new.** Layout primitives exist, but expect rough edges and thin documentation on a fast-moving surface.
